# Общие правила API DTF

## Адреса и версии

| Хост | Что |
| --- | --- |
| `https://api.dtf.ru` | всё, кроме загрузки |
| `https://upload.dtf.ru` | загрузка файлов (`/v2.8/uploader/upload`) |
| `https://leonardo.osnova.io` | картинки по `uuid` |

Версия — часть пути: `/v2.31/feed`, `/v2.10/comments`, `/v2.1/editor`. Это не «версия API целиком»: у каждого эндпоинта своя актуальная версия, и один путь отвечает на нескольких версиях с разными формами ответа. В спецификации в `openapi/` версия указана в каждом пути; если нужна другая, не меняйте её наугад, а сверьтесь с описанием эндпоинта.

Сайт DTF и reDTF ходят на разные версии одних и тех же методов (например, сайт — на `/v2.10/feed`, reDTF — на `/v2.31/feed`). Это не ошибка.

## Формат ответа

Успех (v2): `{ "message": "", "result": … }`, HTTP 200. `result` — объект или массив.

Ошибка (v2): HTTP-статус равен коду, тело `{ "message": "текст на русском", "error": { "code": 403, "info": … } }`. `info` — объект (`{ "errorCode": "USER_BANNED" }`) или пустой массив. Тексты ошибок пишутся для людей и иногда шуточные («Хорошие новости, мы не забыли проверку на права доступа»); логике доверять нужно только коду и `errorCode`.

Ошибка (v3, вход и обновление): `{ "message", "code", "data": null }`, где `code` внутренний (`104`, `105`), а не HTTP.

Исключения: `GET /v2.31/rating` отвечает без `message`, `{ "tabs", "subsites" }`; `POST /v2.1/editor` при ошибке кладёт её в тело, а не в статус — проверяйте `error` и `message.text`.

## Тела запросов

Запросы с телом — `multipart/form-data`, **не JSON**. Поле, содержащее структуру (`entry` в редакторе, `notificationIds` в уведомлениях), — JSON-строка внутри поля формы. Заголовок `Content-Type` вручную не ставьте: у `multipart` нужен `boundary`, его добавит `fetch` с `FormData`.

## Постраничная выдача

Четыре вида, и они не взаимозаменяемы:

| Вид | Где | Как продолжить |
| --- | --- | --- |
| `lastId` + `lastSortingValue` в ответе | `/v2.31/feed`, `/timeline`, `/subsite/subscribers`, `/comments` | передать оба значения из прошлого ответа в следующем запросе (так делает reDTF) |
| `lastId` | `/news` | передать `lastId` |
| `cursor` (строка) | `/v2.10/feed` | как передать — не снималось |
| `nextPage` | `/subsite/subscriptions` | не изучалось, в проверке был `null` |

## Время и числа

Время — Unix-секунды (`date`, `dateModified`, `created`, `until`). id — числа. `lastSortingValue` — дробное число.

## Картинки и видео

В ответах `uuid` вместо адреса. Адрес собирают так:

```
https://leonardo.osnova.io/{uuid}/-/preview/{width}/-/format/webp/
https://leonardo.osnova.io/{uuid}/-/scale_crop/{ширина}x{высота}/-/format/webp/
```

Первая форма — по ширине, вторая — обрезка. Формат (`webp`, `jpeg`) задаёт сегмент `/format/…/`. Для аватарок в списках иногда сразу приходит готовый `avatar_url`. Это те же шаблоны, что использует `getLeonardoUrl` в reDTF; другие трансформации не изучались.

## Параметр `markdown`

`markdown=false` отключает серверную разметку текста: у профиля `description` приходит сырым (так читают биографию), у постов — блоки без markdown-обработки. Если нужен исходный текст, всегда передавайте его.

## Как читать пометки в спецификации

У каждой операции:

- `x-status`: `verified` — работает, подтверждено. Всё, что в спецификации есть, имеет этот статус.
- `x-evidence` — чем подтверждено:
  - `har` — есть в записи трафика сайта DTF;
  - `app` — используется в коде reDTF (запустить его повторно я при составлении не мог, но разработчик им пользуется);
  - `probe` — проверено живым запросом без учётных данных (только публичные методы и формы ошибок).
- `x-checked` — дата последней сверки.

Если в описании сказано «не проверено» или «не снималось», значит так и есть; неизвестное здесь не выдаётся за известное.
